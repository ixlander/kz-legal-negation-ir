## 1. Проект в одном абзаце

Поиск по юридическим текстам путает «вправе» и «не вправе»: dense-эмбеддинги почти не кодируют отрицание. Если retriever принёс статью с обратным смыслом, LLM уверенно ответит противоположное закону. В казахском отрицание — аффикс внутри слова (төле**ме**йді), и токенизатор может его «размазать». Для казахского нет ни бенчмарка юридического поиска, ни устоявшегося NLI-датасета. **Мы строим небольшой бенчмарк на параллельных Ru/Kz статьях Трудового кодекса РК, меряем проблему своими метриками и проверяем, исправляют ли её два дешёвых компонента: BM25, сохраняющий отрицание, и NLI-реранкер.** Фокус — **retrieval**, не генерация.

**Тезис:** fix the evidence before generation, not the size of the generator.

**Связь с интересом преподавателя:** в его материалах прямо поставлен вопрос — правильные ли метрики используются для оценки генеративных систем, и предлагается сделать свою метрику или бенчмарк, в том числе для законодательства. Наш вклад (бенчмарк + свои метрики) отвечает ровно на это.

**Что считается успехом проекта:** таблица B0 → B3 по срезам general/negation и языкам ru/kz с честными интервалами, цифры D1/D2 и разбор ошибок. Работающая система с ответами LLM — **не** цель. Любой исход гипотез — результат, если измерен корректно.

**Материалы:** `docs/current/` — то, что уже показано преподавателю (слайд и речь промежуточной защиты); формулировки гипотез и метрик там совпадают с этим файлом. `docs/papers/` — прочитанные статьи, цитировать только из них. **Старые материалы** (спецификация «Negation- and Time-Aware Legal RAG», бриф, презентация) лежат в `docs/old/` для контекста. Где они расходятся с этим файлом — **прав этот файл** (в них есть время, генерация и 150 вопросов — всё это вырезано).

**Пример, чтобы почувствовать задачу.** Запрос: «Может ли работодатель расторгнуть трудовой договор с беременной работницей?» Правильная статья — та, где сказано «не допускается / не вправе». Рядом в кодексе есть статьи «работодатель вправе расторгнуть трудовой договор в случаях…» — тема та же, смысл обратный. Dense-поиск легко ставит их выше. Наша цель — измерить, как часто это происходит, и проверить, исправляют ли это BM25 с сохранением отрицания и NLI-реранкер. На казахском то же самое, но отрицание сидит внутри слова (`болады` → `болмайды`). (Пример иллюстративный: точные статьи сверить по тексту кодекса.)

**Исследовательский вопрос:** do a morphology-aware BM25 and an NLI reranker retrieve the article with the right polarity, and do they help Kazakh more than Russian?

## 3. Гипотезы (нумерация совпадает со слайдом защиты)

| ID | Утверждение | Метрика | Когда опровергнута |
|---|---|---|---|
| **D1** | e5 ставит юридическую норму ближе к её отрицанию, чем к перефразу | Negation Margin | Средний margin > 0 и доля отрицательных < 20% |
| **D2** | Токенизатор XLM-R/e5 редко выделяет казахский отрицательный аффикс | Affix Isolation Rate | Isolation ≥ 70% |
| **H1** | Морфологический BM25 (B2) сокращает Negation Gap относительно B0, не ухудшая general | Negation Gap, Recall@5 | Разница в пределах 95% CI или general падает |
| **H2** | NLI-реранкер (B3) лучше и обычного реранкера (B3′), и правила (B3-rule) на negation-срезе | Twin-above-Gold, Recall@5 | B3′ или B3-rule не хуже B3 |
| **H3** | Прирост от B2/B3 на казахском больше, чем на русском (на тех же статьях) | Δ метрик Kz vs Ru | Приросты сопоставимы (в пределах CI) |
| **H5** | Добавление XNLI-tr улучшает реранкер на казахском | NLI F1 (kz), Twin-above-Gold (kz) | Нет прироста |
| **H6** | Entailment-контрпримеры («не менее») снижают ложные contradiction | Range-negation Error | Нет снижения |

H4 из старой спецификации влита в H3. D3 из старой презентации заменена Twin-above-Gold для B0.
**Опровергнутая гипотеза, измеренная корректно, — тоже результат.** Не подгоняй.

## 4. Конфигурации (ablation ladder)

| # | Конфигурация | Проверяет |
|---|---|---|
| B0 | Dense only: `intfloat/multilingual-e5-base` (префиксы `query: ` / `passage: `) | baseline, D1 на уровне поиска |
| B1 | B0 + BM25 без морфологии, RRF (k=60) | вклад лексики как таковой |
| B2 | B0 + морфологический BM25 (отрицание сохраняется), RRF | H1, H3 |
| B3′ | B2 + обычный мультиязычный реранкер (`jinaai/jina-reranker-v2-base-multilingual`, проверить загрузку) | контроль к H2 |
| B3-rule | B2 + правило: буст статей, у которых полярность совпадает с запросом | контроль к H2 |
| B3 | B2 + дообученный NLI-реранкер (XLM-R) | H2, H3, H5, H6 |

Реранкер работает по top-30 из B2, итог — top-10.
**Скоринг NLI-реранкера — открытый вопрос:** S1 = P(entail) − P(contradict), S2 = P(entail) + P(contradict) («решительность»). Статья «не вправе» может быть правильным ответом, поэтому S1 может топить gold. Выбор — на dev-части (см. 5.3), не на тесте.

### Морфология
- **Ru:** `pymorphy3` лемматизация; стоп-слова удаляются, **кроме «не» и «ни»**.
- **Kz:** lowercase + regex: в глагольных формах с отрицательным аффиксом (`-ма/-ме/-ба/-бе/-па/-пе` перед окончаниями вроде `-йды/-йді/-ған/-ген/-у/-с`) отделить основу и добавить токен `NEG`. Частицы `емес`, `жоқ` сохраняются как есть. Точность стеммера проверить на выборке ≥100 слов вместе с владельцем (ложные срабатывания на словах, где «ма/ме» не отрицание).
- **Ловушка:** вопросительные частицы `ма/ме/ба/бе/па/пе` («келесің бе?») совпадают по форме с отрицательными аффиксами. Обычно они пишутся отдельным словом — стеммер должен трогать только аффикс **внутри** глагольной формы, а отдельно стоящие частицы не считать отрицанием. Также «ма/ме» встречаются внутри обычных основ — поэтому матчим аффикс только перед глагольными окончаниями, а не в любом месте слова.

### Rule-based polarity booster (B3-rule)
1. Полярность запроса: `NEG`, если в нём есть «не/нельзя/запрещ*/не допускается» (ru) или `NEG`-токен/`емес`/`жоқ`/`болмайды` (kz); иначе `POS`.
2. Полярность чанка — тем же правилом по предложению с наибольшим лексическим пересечением с запросом.
3. Итоговый скор: `score_B2 + α`, если полярности совпадают, `score_B2 − α`, если нет; α подбирается на dev.
Это намеренно глупый бейзлайн: если NLI-реранкер его не обходит, NLI не нужен.

## 5. Данные

### 5.1. Корпус
- Источник: adilet.zan.kz, Трудовой и Налоговый кодексы РК (`/rus/docs/...` и `/kaz/docs/...`). Сайт рендерит текст через JS → Playwright. Если скрапинг тормозит больше 1,5 ч — fallback: владелец сохраняет страницы из браузера, мы парсим HTML.
- Формат: `data/corpus/{labor,tax}_{ru,kz}.jsonl`, поля: `chunk_id, code, article_no, para_no, lang, title, text`.
- Выравнивание Ru↔Kz по `article_no` (+`para_no`). Проверить вручную 10 случайных пар на каждый кодекс.
- Налоговый кодекс большой и с таблицами/формулами: таблицы не индексируем как текст (или храним отдельным чанком с пометкой), чанк по пунктам статьи.
- **Папка преподавателя `data/raw/teacher_law/`:** PDF/DOCX девяти кодексов, **только русский, редакция ~апрель 2024**. Трудовой кодекс там с чистым текстовым слоем (204 статьи, сноски «Сноска. Статья N с изменениями…» внутри текста). Использовать **только** для быстрых пилотов (D1) и как fallback-образец разметки. В бенчмарк не брать: казахская версия с adilet будет другой редакции, и пары Ru/Kz разъедутся.
- `app.py` и `llama2 notebook.ipynb` из папки преподавателя **не класть в репозиторий** (в ноутбуке открытый HF-токен). Это базовый llama-index RAG-шаблон, для проекта не нужен.

### 5.2. Оценочный набор (главный актив, делается ДО обучения моделей)
- `data/eval/queries.jsonl`, поля: `qid, pair_id, lang, slice (general|negation), question, gold_ids[], twin_ids[], split (dev|test), notes`.
- Сначала пишутся 50 вопросов на русском, потом казахские версии тех же вопросов (`pair_id` общий). Казахские — `NEEDS_KZ_CHECK`, пока не проверены.
- **general:** ответ не зависит от полярности («какова продолжительность ежегодного отпуска?»).
- **negation:** ответ меняется, если поиск перепутает «можно/нельзя» («может ли работодатель уволить беременную работницу?»). В запросе «не» может и не быть.
- `twin_ids` — статья(и) на ту же тему с противоположной полярностью. Если естественного близнеца нет — пусто, такие вопросы исключаются из Twin-above-Gold (долю указать).
- Split: **по 5 пар из каждого среза → dev** (настройка скоринга, порогов), остальное → test (только отчёт).
- Агент может предлагать черновики вопросов, но **gold/twin финализирует владелец** по тексту кодекса.

### 5.3. NLI-данные
- XNLI ru и tr: **subsample по ~50–100k пар на язык** (полный объём не нужен и не влезет в Colab-сессию).
- TERRa — бинарный (entailment / not_entailment). Не смешивать с 3-классовой разметкой без явного решения; по умолчанию не используем.
- Синтетика из корпуса: 3–5k пар. Правила: ~30% пар с отрицанием → entailment (двойное отрицание, «не менее / не позднее / не более»); contradiction делаются не только вставкой «не», но и заменой модальности («вправе» ↔ «обязан не», «допускается» ↔ «запрещается»).
- Ручной валид: `data/nli/val_manual.jsonl`, 100 пар, **ни один шаблон не пересекается с генератором синтетики**.

## 6. Метрики (определения зафиксированы)

| Метрика | Определение |
|---|---|
| **Negation Margin** (D1) | `cos(s, paraphrase) − cos(s, negation)` на e5 (`passage: `-префикс, нормированные векторы). Отчёт: среднее, медиана, доля < 0, отдельно Ru и Kz |
| **Affix Isolation Rate** (D2) | Доля казахских отрицательных форм, где граница токена XLM-R проходит **и перед, и после** отрицательного аффикса. Дополнительно: доля, где есть хотя бы одна граница. Контроль: доля русских «не», ставших отдельным токеном |
| **Recall@k** (k=5,10), **MRR@10** | Стандартные, по `gold_ids` |
| **Negation Gap** | `Recall@5(general) − Recall@5(negation)` на тех же языке и конфигурации |
| **Twin-above-Gold** | Доля negation-запросов (с непустым `twin_ids`), где лучший twin стоит выше лучшего gold в полном рейтинге |
| **Pairwise accuracy** | Как в NevIR, только для сопоставимости, на парах вопросов с общим twin |
| **NLI F1 / Contradiction recall** | На ручном валиде, раздельно ru/kz |
| **Range-negation Error** (H6) | Доля пар с «не менее / не позднее / не более» из валида, ошибочно предсказанных как contradiction |

**Статистика:** у нас ~20 test-запросов на срез и язык → интервалы широкие. Для каждой разницы между конфигурациями — paired bootstrap, 1000 ресемплов, 95% CI. Писать «улучшение» только если CI не пересекает 0. Иначе — «разницы не обнаружено».

## 11. Контекст из литературы (проверено по PDF)

- **NevIR reproduction** (van den Elsen et al., SIGIR 2025), Table 1, pairwise accuracy (random 25%, humans 100%): большинство bi-encoder'ов 6,5–22,6%; nli-deberta-v3-base (MNLI, zero-shot) 30,2%; jina-reranker-v2-base-multilingual 65,2%; RankGPT o3-mini 77,3%; после дообучения на NevIR cross-encoder ≈75%, bi-encoder ≈50%. Дообучение на отрицании может ухудшать обычный поиск (MS MARCO). Только cross-encoder обобщается между NevIR и ExcluIR.
- **Magesh et al., 2025** (J. Empirical Legal Studies): Lexis+ AI и Westlaw (RAG) галлюцинируют в 17–33% случаев.
- **Toraman et al., 2023** (ACM TALLIP): токенизация для турецкого; морфологический токенизатор конкурентен с BPE/WordPiece; пример «vermedim», суффикс -me = отрицание.
- Цифра «cosine ≈0.93–0.97» из старой спецификации **не проверена** — не использовать, пока не получим свою из D1.
